# 逻辑图模板 — 项目顶层控制图

> 用途：从本模板生成/核对项目根目录 `逻辑图.MD`。每次代码、配置、计划任务或需求变更后，按 §C 核对清单逐节校验，保证逻辑图始终反映当前真实行为。
> 填写规则：所有判定必须能追溯到代码/配置出处；不写"应该"，只写已验证行为。

## §1 总目标

- 一句话目标：（项目无人值守要完成什么）
- 成功判据：列 3–6 条**全部满足才算达成**的可验证条件，每条可对应一条命令或一份运行产物。

## §2 目标分解（G0–Gn）

| 阶段 | 目标 | 前置条件 | 未达标处置 |
|---|---|---|---|
| G0 | （环境/依赖就绪） | | （诊断入口） |
| G1..Gn | （按业务主链路逐段拆） | | （失败时的确定行为，禁止"看着办"） |

规则：阶段编号稳定，新增阶段往后追加，不重排旧编号。

## §3 主链路决策流程图

```text
触发源 → ◇判定门 → 动作 → ◇判定门 → … → 终态
```

规则：
- 判定用 `◇GATE-XXX`，每个分支必须写明去向；不允许无出口的判定。
- 串行/并行关系必须显式标注。
- 与代码流程不一致时，以代码为准修图。

## §4 判定条件总表（Gate 清单）

| Gate | 判定内容 | 通过 → 动作 | 失败 → 动作 | 配置来源 |
|---|---|---|---|---|
| GATE-XXX | （可判真伪的条件） | | | （config 键 / 文件） |

规则：每个 Gate 必须有配置来源或代码出处；新增判定先进此表，再进流程图。

## §5 任务状态机

```text
状态 → 事件 → 下一状态（标注终态、禁止迁移）
```

规则：区分业务状态与回执状态；标明哪些状态禁止自动重试。

## §6 不变量（不可违背）

列 3–8 条无论怎么改代码都必须成立的约束（安全、串行、幂等、凭据边界）。与其他文档（如 INDEX.md）重复时，保持逐字一致。

## §7 当前状态快照

- 模式/开关当前值、账户/任务清单（日期标注）
- 已知缺口：K1、K2…（现象 → 修复方向；修复后移除或标记已闭环）
- 最近一次真实验证：日期 + 结果

规则：本节是"活文档"，每次验证后更新日期与结果。

## §8 变更同步对照表

| 变更对象（文件/目录/配置域） | 必查并同步的节 |
|---|---|

规则：覆盖项目全部代码目录与配置入口；新增模块必须在此登记。

## §9 AI 协作规则

1. 改前读本图，定位影响的 Gate/阶段。
2. 改后同步本图 + §7 快照，附验证证据。
3. 图与代码冲突时以代码为准修图，并在 mission 记录。

## §C 核对清单（每次变更后过一遍）

- [ ] 改动涉及的 Gate 在 §4 中存在且判定/处置仍正确
- [ ] §3 流程图与新代码路径一致，无无出口判定
- [ ] §5 状态机覆盖新增/变更状态
- [ ] §6 不变量未被违反
- [ ] §7 快照日期、开关值、缺口清单已更新
- [ ] §8 对照表覆盖本次改动的所有文件
- [ ] 全文 ≤500 行；与 specs/*.md、INDEX.md 无冲突
